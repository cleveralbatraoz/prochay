# Правила для агентов

## Работа через GitHub

- `main` содержит текущую рабочую версию. Для одной задачи создай короткоживущую ветку от актуального `main`. Локальные итерации можно делать без коммитов. Каждый результат, готовый к ревью, фиксируй коммитом.
- Открой PR в `main` и пришли владельцу ссылку.
- Текст описания PR состоит только из коротких тезисов об итоговых изменениях относительно целевой ветки, от самого важного к деталям. Формулируй пункты без обращений к читателю, описания методики проверки и истории правок.
- При каждом обновлении PR сверь описание с текущим diff относительно целевой ветки. Обнови список изменений и убери пункты, утратившие актуальность.
- Для визуальных изменений прикладывай к PR только скриншоты. Видео для ревью не записывай.
- Владелец оставляет замечания в GitHub. Исправления добавляй новыми коммитами в тот же PR. Только владелец нажимает **Squash and merge**. Один принятый PR даёт один коммит в `main`.

## Макеты и проверка

- [Дизайн-док](design/spec.md) хранит согласованные решения по дизайну приложения. Агент переносит сюда договорённости из обсуждений. Doop хранит рабочий макет. К ревью сохрани в `design/doop/` разметку экранов, компоненты, токены и сведения о фреймах и стартовых точках переходов, нужные для чтения этой версии.
- Для дизайн-PR сделай отдельную копию актуального холста Doop (для первого прототипа создай холст). Ссылки на холст и плеер храни в дизайн-доке ветки. В описание PR их не включай. До слияния используй ту же копию для всех правок. Для правок только документации отдельный холст не нужен.
- Называй основной холст Doop и каждую его копию «ПРОЧАЙ». В `design/doop/.doop/config.json` указывай это же имя и ID холста текущей ветки.
- Экраны редактируй через [Doop MCP или CLI](https://doop.design/docs/cli). Переходы проверяй в [плеере](https://doop.design/docs/prototypes) через Playwright в отдельном headless Chromium с собственной сессией.
- После слияния дизайн-PR проверь ссылку на плеер в `main`. Оставь текущий холст и копии для открытых дизайн-PR. Удали прежний холст, когда сверишь, что он больше никому из них не нужен. При закрытии PR без слияния удали его черновую копию. Завершённую ветку убери.
- После слияния изменений макета [опубликуй демо из `main`](design/publish/README.md) и проверь переход из каталога в карточку по публичной ссылке.

## Файлы

- Стек и границы компонентов описаны в [архитектуре мобильного приложения](docs/architecture.md).
- Пиши код приложения и скрипты проекта на TypeScript (`.ts`), React-компоненты с JSX — на TSX (`.tsx`). Для запуска скриптов и сборки используй Node.js. Зависимости устанавливай через npm и фиксируй в `package-lock.json`.
- Не пиши комментарии в файлах проекта.
- Исходные фотографии, шрифты и другие нужные бинарные ресурсы храни в `design/assets/` через Git LFS. Перед добавлением бинарника проверь его правило в `.gitattributes`. Бюджет проекта на перерасход LFS — $0. Перед первой загрузкой ресурсов проверь ограничение в GitHub Billing.
- Временные снимки, записи и отчёты Playwright, ключи и данные входа храни вне истории Git.

# ПРОЧАЙ — мобильное демо

Демо магазина ПРОЧАЙ для личного показа владельцам на iOS и Android. Сейчас согласуем процесс и архитектуру. К проектированию экранов и реализации переходим по решению владельца. Используем бесплатные инструменты.

## Работа через GitHub

- `main` содержит текущую рабочую версию. Для одной задачи создай короткоживущую ветку от актуального `main`. Локальные итерации можно делать без коммитов. Каждый результат, готовый к ревью, фиксируй коммитом.
- Открой PR в `main` и пришли владельцу ссылку. В описании кратко укажи по убыванию важности результат, где его посмотреть и что проверено. Для визуальных изменений дай ссылку на плеер и приложи к PR скриншоты, нужные для сравнения.
- Владелец оставляет замечания в GitHub. Исправления добавляй новыми коммитами в тот же PR. Только владелец нажимает **Squash and merge**. Один принятый PR даёт один коммит в `main`.

## Макеты и проверка

- [Дизайн-док](design/spec.md) хранит задачу, поведение и критерии проверки экранов. Агент переносит сюда договорённости из обсуждений. Doop хранит рабочий макет. К ревью сохрани в `design/doop/` разметку экранов, компоненты, токены и сведения о фреймах и стартовых точках переходов, нужные для чтения этой версии.
- Для дизайн-PR сделай отдельную копию актуального холста Doop (для первого прототипа создай холст). Ссылку на его плеер добавь в PR и в дизайн-док ветки. До слияния используй ту же копию для всех правок. Для правок только документации отдельный холст не нужен.
- Экраны редактируй через [Doop MCP или CLI](https://doop.design/docs/cli). Переходы проверяй в [плеере](https://doop.design/docs/prototypes) через Playwright в отдельном headless Chromium с собственной сессией.
- После слияния дизайн-PR проверь ссылку на плеер в `main`. Оставь текущий холст и копии для открытых дизайн-PR. Удали прежний холст, когда сверишь, что он больше никому из них не нужен. При закрытии PR без слияния удали его черновую копию. Завершённую ветку убери.

## Файлы

- Исходные фотографии, шрифты и другие нужные бинарные ресурсы храни в `design/assets/` через Git LFS. Перед добавлением бинарника проверь его правило в `.gitattributes`. Бюджет проекта на перерасход LFS — $0. Перед первой загрузкой ресурсов проверь ограничение в GitHub Billing.
- Скриншоты для ревью прикладывай к PR. Временные снимки, записи и отчёты Playwright, ключи и данные входа храни вне истории Git.

## Архитектура будущей реализации

- **Клиент.** Expo, React Native и TypeScript. Общие экраны для обеих платформ, навигация через Expo Router и нативный Stack. Для оформления — `StyleSheet` и общая тема. Короткий чайный акцент на переходе — встроенный `Animated`. Действия доступны во время анимации.
- **Данные.** Вручную подготовленный каталог и фотографии входят в сборку и работают офлайн. Экраны получают модели товаров через асинхронный контракт каталога. Источник выбирается в одном месте. Будущий адаптер сайта или API должен подключаться без изменений в коде отображения.
- **Компоненты.** Экран связывает данные с действиями. Визуальные компоненты получают модель и обработчики через параметры. Прямой импорт файла каталога допустим только в адаптере.
- **Состояние.** Корзина и избранное общие для экранов и живут в памяти через Context и `useReducer`. Избранное хранит ID товара, корзина — ID фасовки и количество. При новом запуске оба списка пусты.
- **Проверка.** Компонентные тесты используют React Native Testing Library и тестовые данные. Перед показом проверяем путь из каталога в корзину, возврат к прежней позиции и плавность переходов на iOS и Android.

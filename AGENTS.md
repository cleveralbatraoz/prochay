# Правила для агентов

Каждое изменение архитектуры или стека сначала согласуй с владельцем проекта. Объясни, что предлагаешь изменить и зачем. Приступай к реализации только после его явного согласия.

## Работа через GitHub

- `main` содержит текущую рабочую версию. Для каждой задачи создай короткоживущую ветку от актуального `main` и веди всю разработку в отдельном Git worktree для этой ветки. Локальные итерации можно делать без коммитов. Каждый результат, готовый к ревью, фиксируй коммитом.
- Открой PR в `main` и пришли владельцу ссылку. Для ревью приложения [собери и запусти версию PR локально](design/publish/README.md) на компьютере владельца. Проверь в чистой гостевой сессии, что каталог открывается сразу, без входа в аккаунт. Первой дай ссылку на запущенное демо, затем — на PR.
- Добавляй ссылку на запущенное демо в описание PR.
- Текст описания PR, кроме ссылки на демо, состоит только из коротких тезисов об итоговых изменениях относительно целевой ветки, от самого важного к деталям. Формулируй пункты без обращений к читателю, описания методики проверки и истории правок.
- При каждом обновлении PR сверь описание с текущим diff относительно целевой ветки. Обнови список изменений и убери пункты, утратившие актуальность.
- Исправляй причину каждого предупреждения и каждой ошибки при установке зависимостей, сборке, проверках, запуске и публикации. Перед открытием и каждым обновлением PR проверяй затронутые команды и консоль приложения. Критерий готовности — ноль предупреждений, ошибок и известных уязвимостей зависимостей по `npm audit`. Сохраняй диагностику включённой.
- Прикладывай скриншоты только к PR, в которых внешний вид экранов отличается от целевой ветки и разницу видно на снимке. Видео для ревью не записывай.
- Владелец оставляет замечания в GitHub. Исправления добавляй новыми коммитами в тот же PR. После успешных проверок в GitHub Actions только владелец нажимает **Squash and merge**. Один принятый PR даёт один коммит в `main`.

## Макеты и проверка

- Не пиши тесты.
- Демо находится в разработке. Поддерживай только актуальные ссылки на экраны. При изменении адреса обновляй ссылки в проекте.
- Согласованные решения по дизайну фиксируй в [дизайн-доке](design/spec.md). Рабочая версия экранов хранится в Git как HTML и CSS, данные каталога — в JSON.
- Переходы и взаимодействия проверяй в гостевой сессии Playwright в отдельном headless Chromium.
- В корневом README показывай скриншоты каталога и карточки товара из демо. Если меняется вид экрана или данные, видимые на снимке, пересними этот экран из сборки того же PR при размере окна 390 × 844 и обнови снимок в этом PR. Храни скриншоты README в `design/assets/readme/` через Git LFS.
- После слияния дождись автоматической публикации `main` на GitHub Pages и проверь переход из каталога в карточку по публичной ссылке. Затем останови локальное превью PR и заверши работу с его веткой.

## Файлы

- Описывай в документации действующее устройство проекта и поведение приложения. Для разовых операций указывай условие, при котором они нужны.
- Стек и границы компонентов описаны в [архитектуре мобильного приложения](docs/architecture.md).
- Пиши код приложения и скрипты проекта на TypeScript (`.ts`), React-компоненты с JSX — на TSX (`.tsx`). Для запуска скриптов и сборки используй Node.js. Зависимости устанавливай через npm и фиксируй в `package-lock.json`.
- Не пиши комментарии в файлах проекта.
- Исходные фотографии, шрифты и другие нужные бинарные ресурсы храни в `design/assets/` через Git LFS. Перед добавлением бинарника проверь его правило в `.gitattributes`. Бюджет проекта на перерасход LFS — $0. Перед первой загрузкой ресурсов проверь ограничение в GitHub Billing.
- Временные снимки, записи и отчёты Playwright, ключи и данные входа храни вне истории Git.
